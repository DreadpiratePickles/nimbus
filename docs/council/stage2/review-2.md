## 5. What all four missed

1. **The tool is itself a crown jewel and nobody threat-modelled it.** B (IG7) and D (item 5) propose storing raw provider JSON per resource version; raw Lambda/ECS/Function-App configuration includes environment variables, which routinely hold secrets. No response defines a redaction contract for stored raw JSON, DB-at-rest protection or file permissions for the SQLite file that now holds a complete map of every attack path, or retention rules for that DB when it is produced inside a GitHub Action (artifact retention = publishing the attack map). A red-teamer's first question.
2. **What leaves the machine on the LLM path.** AI4 guardrails wrap untrusted tag data against injection, but none of the four minimises *outbound* content: resource names, tags, policy documents and raw config go to the chosen model. A buyer's privacy reviewer asks for an allowlist of fields sent to the model and a redaction test, not a provider abstraction.
3. **Prowler framework import is not "parity in a week".** Prowler's 105 JSONs map requirements to ~1,616 Prowler check IDs; nimbus's alias table covers 58 and runs 75 canonical checks. Imported frameworks will be mostly dangling references unless Prowler output is ingested, so each framework must carry an honest denominator ("31 of 240 requirements assessable natively, 190 via Prowler ingest, 19 manual") — the OS #3 "7 of 212" rule applied to frameworks. A and B both claim near-parity; neither states the coverage number.
4. **Collector scale and scan-duration SLO.** D designs traversal scale; nobody designs collection scale: per-account parallelism, API throttling budgets, pagination cost, and "how long does 200 accounts take?" (`scan.parallel` unset currently forces concurrency 1 — verifier note). A buyer with 200 accounts asks this in the first call.
5. **Terraform-only code-to-cloud.** Every plan-time-diff, patcher and cloud-to-code design assumes Terraform state and HCL. Azure buyers use Bicep, AWS-native shops CloudFormation/CDK, platform teams Pulumi. No response even names the gap or says "Terraform first, others ingest Checkov output".
6. **Role split for write-capable operations and legal basis for probes.** TS3's generated read-only policy is a trust asset, but `onboard --deploy`, `offboard --rollback`, `verify` targeted re-collect and `fix --apply` need write permissions; nobody separates a scan role from an operator role. C's consent file for AP9 probes is the only mention of authorisation; a buyer's counsel asks who is permitted to port-scan what.
7. **Repo hygiene a red-teamer reads first.** `.planning/STATE.md` states that a git-ignored env file holds a live GitHub token and asks for rotation "if it was ever shared". A security tool whose planning docs advertise where a live token sits fails the trust-kit story regardless of cosign. Rotate, remove the sentence, and add nimbus's own secret-scan hook to the release gate.
8. **Dedup against in-flight work** (process, §0 above): all four wrote their two-week lists against a tree that two fix tracks were changing underneath them.
