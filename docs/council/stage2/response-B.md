# Council stage 1 — the council member / RFP-buyer council member

_Written 2026-10-09 for `docs/council/QUESTION.md`. council member: a head of cloud security at a 500–5,000-person company who has run CSPM/CNAPP RFPs in 2024–2026, bought Wiz, Orca or Cortex at least once, and whose team gets more alerts per week than it can read. I judge a tool by three gates: does it get **shortlisted** (it answers the RFP sheet), does my team **trust** it (no false criticals, no self-inflicted breach, evidence for every claim), and does it get **adopted** (fewer, truer things to do, delivered where engineers already work). Every competitive claim below cites the research under `docs/research/`; every "nimbus today" claim cites `docs/research/nimbus-capability-inventory.md` (INV), `docs/benchmark.md`, or `docs/sessions/2026-10-09-cwm-ui.md`. No market number here is mine._

Sections follow the order in QUESTION.md: (1) verdict on plan v2, (2) what is missing for "complete package", (3) 12-month roadmap with 5 bets and 5 cuts, (4) first 10 engineering items, (5) biggest risk, then (6) the implementation plan — capability map, sequenced phases, exit criteria, claims — which is the largest section.

## 1. Verdict on `IMPLEMENTATION_PLAN_v2.md`

**Overall: the right spine, the wrong width.** The plan correctly puts truth before features and picks the one loop nobody else ships (path → explain → PR → verify). But it is written for an engineer who wants a sharper tool, not for a buyer who scores 21 criteria on a sheet, and it still describes a product that has never touched a real cloud account.

### What it gets right

1. **Phase 0 "Trust & truth" first.** A security product that edits the wrong Terraform resource (INV defect 7), never resolves findings (defect 19) or has a bypassable read-only SQL guard (defect 1) is disqualified in the first week of a proof-of-value. Fixing these before any feature is exactly what I would demand. The hardening remediations in INV "Remediated 2026-10-09" are the kind of evidence (failing test first, independent re-probe) that makes me believe a vendor.
2. **Issues, not findings (Track G).** The most quoted complaint about Wiz is tickets that "appear and disappear magically in hundreds" (`docs/research/strategy-how-to-win.md` §1.3). An Issue object with stable identity, state and `resolved_at` is the fix for that. Good.
3. **The wedge loop (Phase 1 items 1, 2, 4).** Plan-time path diff in the PR, root-cause plans and a verified fix are the three things that would make my platform team *want* the tool rather than tolerate it. The matrix confirms no vendor combines plan + live graph in a PR (`docs/research/competitive-feature-matrix.md` AP10) and no vendor computes a minimum fix set (AP6).
4. **Release trust kit (Track E) and the "zero egress" exit criterion.** After the Trivy v0.69.4 compromise (76 of 77 `trivy-action` tags force-pushed; `docs/research/competitive-feature-matrix.md` "Supply-chain incidents") I now ask every vendor for signed artefacts, pinned actions and the read-only policy they need. A free tool that can show cosign, SLSA and a generated least-privilege policy clears a bar many paid tools miss.
5. **The published benchmark (Track H).** `docs/benchmark.md` with recall 12/12, recall@7 10/12, precision 95.2% on a labelled lab is the single most persuasive artefact in the repo. Nobody, open or commercial, publishes path-level ground truth (`docs/research/strategy-how-to-win.md` §7.3).
6. **The "Not doing" list** (host agents, EDR, JIT brokering, SaaS, snapshot scanning, auto-merge, check-count races, Cyera-grade DSPM, GRC workflows, SAST). Every one of those is a trap for a small team; `docs/research/nimbus-gap-analysis.md` §f gives the right reasons.
7. **North-star metric "paths closed through merged PRs".** That is the number I would put in my board deck.

### What it gets wrong, or leaves out

1. **It still treats the live-cloud run as a blocker to be recorded, not as the first item.** `.planning/STATE.md` line 2 and INV §18: nothing has run against AWS, Azure or GCP. Verification 2 (session log) confirms "Live-cloud behaviour (real IAM, StackSets, doctor identity clients) is still unverified: fakes only." From my chair this means the benchmark is synthetic and every collector claim is a hypothesis. The plan says "first live run is the top item once Bobby provides lab credentials". Make it the top item, period: open a lab account this week, run `lab/terraform/aws` under `NIMBUS_E2E=1`, and publish the first live numbers next to the synthetic ones.
2. **Phase 0 is not done.** QUESTION.md says Phase 0 was "done this session"; the second verifier found a new HIGH (D1: module-aware tfstate mapping patches the wrong module's file, `internal/iac/iac.go:221-254`) and a process-killing stack overflow in `scan --iac` (D3), plus eight collector false-pass/false-positive classes still open (Track C partials: `IsAdmin` 8 of 14 adversarial cases wrong; GCP priority 0; port ranges judged by lowest port; M365 `OR` operator; Okta risk conditions) and an `offboard --rollback` that will delete another account's role. Phase 0 exit criterion (a) "all inventory top-20 defects closed with tests and re-probed" is not met. The plan must say so.
3. **It optimises for three wedges; an RFP scores 21 criteria.** rfp.wiki's CNAPP/CSPM template weights Product & Technology at 43% across nine criteria (multi-cloud coverage, misconfiguration depth, identity posture, remediation automation, alert-noise control, IaC shift-left, runtime-to-posture correlation, executive reporting, data residency), Security & Compliance 14%, Commercials 24% (`docs/research/competitors/compliance-and-adjacent.md` F5). Plan v2 pushes framework breadth, OCSF/ASFF, governance/SLA, executive reporting, Azure RBAC/GCP IAM and org-wide onboarding into Phases 2–3. A buyer who cannot tick "SOC 2, PCI, ISO, NIST mapped" or "sends to Splunk/Security Hub" in month one does not shortlist, however good the paths are. An "RFP floor" track must run in parallel with the wedge loop from Phase 1.
4. **Identity is under-weighted and sequenced too late.** Datadog's 2025 data: 59% of AWS IAM users have keys older than a year, 19.4% of EC2 instances are overprivileged, only 1% of buckets are effectively public (`docs/research/strategy-how-to-win.md` §3.1A). Risk has moved to identity. Yet the effective-permission evaluator (gap analysis O16, matrix ID1) sits at the top of Phase 2, while every attack path and every "who can read PII" answer in Phase 1 depends on it. A single wrong "admin" or "can read" in a live demo is the kind of error a red teamer on my staff will catch in ten minutes. Pull a v1 evaluator (explicit Deny, NotAction/NotResource, the common condition keys, SCP deny) into Phase 1.
5. **Compliance is demoted to a "support feature".** In the 500–5,000 segment the CISO's budget line for CSPM is justified by SOC 2 / ISO 27001 / PCI renewal, and the auditor is the person who sees the output. Prowler ships 105 framework files (`docs/research/competitive-feature-matrix.md` CO1); nimbus has 11 hand-written frameworks with PCI "4.0" using 3.2.1 IDs and Go/Python counts that disagree (INV §8). That is a disqualifier in the first auditor meeting. Porting Prowler's Apache-2.0 framework JSON with attribution plus a catalogue integrity test (gap analysis O39) is cheap breadth that the plan defers to Phase 2.
6. **No exception workflow, no notification hygiene.** Mutes with mandatory reason, expiry and approver (matrix RP7) and routing/dedup with a "new results only" mode (IW1) are how a team survives the first scan. Plan v2 does not mention either. Combined with Issues, this is where nimbus can beat the "tickets appear and disappear" complaint outright.
7. **Runtime-to-posture correlation is treated as out of scope rather than as an ingest problem.** I agree nimbus must never ship an agent. But "runtime-to-posture correlation" is a named rfp.wiki criterion and the number-one table-stakes gap in the gap analysis §b. The cheap, honest answer is to ingest GuardDuty, Defender, Falco and SCC alerts as evidence on graph nodes and raise an Issue when an alert lands on a resource that sits on a path (gap analysis §f already says so; the plan does not schedule it).
8. **The cwm dashboard keeps absorbing effort.** Executive dashboards and reporting are a cross-vendor complaint (`docs/research/competitive-feature-matrix.md` "Repeated buyer complaints") and the one place a CISO looks personally. An OpenBSD-window-manager aesthetic is a power-user delight and an executive liability. The plan should freeze the UI after Track I and put the effort into a plain HTML/PDF executive report with trend, MTTR and compliance %.
9. **Team mode is cut entirely.** Full multi-tenant and MSP mode should stay cut (gap analysis O60 ranks last). But "do you support SSO?" is a gating question on every security questionnaire I have ever filled in, and a shared bearer token on a self-hosted server will fail my own internal review. A minimal OIDC login with two roles (viewer/admin) and an audit log for the self-hosted server belongs in the plan by Q2 2027; SCIM, RBAC depth and multi-tenant can be the paid tier.
10. **Nothing on docs.** "Closed docs" is a repeated complaint about Wiz (`docs/research/strategy-how-to-win.md` §3.1D). nimbus has README overclaims (INV §17) and no docs site. A ten-minute quickstart, the generated IAM policy page and a per-command reference are part of being shortlistable.

### The five bets

1. **The benchmark is the marketing.** Nightly live lab (AWS now, Azure/GCP in Q1) plus Prowler, Checkov and Trivy run on the same estate, re-published per release with raw outputs. No vendor can match this because Wiz and Orca keep closed formulas (`docs/research/strategy-how-to-win.md` §4b). This is also the only thing that makes my red team stop arguing.
2. **The loop: plan-time path diff + verified fix.** The distribution engine (Checkov's 3.97M PyPI downloads a month versus Prowler's 104k is a placement effect, `docs/research/strategy-how-to-win.md` §2.1) and the trust engine (nothing is "fixed" until re-collected). Both unique per the matrix (AP10, RM4 free).
3. **Effective IAM as the precision engine.** Deny/NotAction/conditions/SCP/RCP/boundaries/resource policies, with `who-can` and right-size PRs. It is the hardest item and the one that decides whether paths are true. The open-source field here is dormant (PMapper last release 2022) or brand new (AWSHound, pathfinding.cloud) — `docs/research/strategy-how-to-win.md` §3.1C, `docs/research/competitive-feature-matrix.md` "Dormant OSS".
4. **Evidence an auditor accepts.** Prowler-ported framework breadth with integrity CI, a signed evidence bundle with period coverage ("control effective X of Y days"), and a Vanta/Drata export. AWS Audit Manager closed to new customers 2026-04-30 (`docs/research/competitive-feature-matrix.md` market signals) — a timely hole.
5. **"The security tool that cannot hurt you."** Signed/SLSA releases, generated read-only policy, zero egress by default, coverage honesty, read-only MCP, offboard rollback, no auto-merge. After Trivy and KICS in 2026 this is a buying criterion, and it is a business-model conflict for SaaS CNAPPs (`docs/research/strategy-how-to-win.md` §4g).

### The five explicit cuts

1. **The cwm dashboard as an investment target.** Freeze after Track I. Maintenance only. All reporting effort goes to the static HTML/PDF executive report and the CLI. Rationale: cross-vendor "weak executive dashboards" complaint (`docs/research/competitive-feature-matrix.md` "Repeated buyer complaints"); STRAT §7.2 already recommends CLI + static report as the first-run surface.
2. **The cost/ROI module beyond one card.** Delete the `$4.88M × (1−e^(−Σscore/50))` ROI formula and double-counted savings (INV §11). Keep one "security-driven savings" card with visible inputs. Rationale: STRAT §4f — no evidence buyers choose a CSPM for cost; a bogus ROI number costs more credibility than it earns.
3. **Duplicate Python implementations of Go logic.** Python `checks/` (Prowler-style boto3 checks), Python `compliance/engine.py` as a second mapping engine, Python `ensure_views` that reverts Go's lifecycle views (verifier-2 defect 7). One implementation per number: Go computes, Python renders and talks. Rationale: INV §8 Go/Python drift; plan principle "one implementation per number".
4. **New native collectors and check-count growth** (Vercel, Cloudflare, MongoDB Atlas, more M365 checks). Ingest Prowler for breadth; spend native effort only on what the graph needs (identity edges, exposure, relationships). Rationale: STRAT §1.5 "checks are a commodity"; Prowler's 2,396 commits a year is a treadmill nimbus cannot win.
5. **The polling "real-time" monitor as a product claim, plus Neo4j/Neptune sink work, the VS Code extension (freeze), JIT brokering, agentless snapshot scanning, in-account DSPM sampler, FAIR dollars.** Monitor becomes an input to the Issue timeline (who changed what), not an alerting product. Rationale: INV §10 alert storms; gap analysis §f for the rest.

## 5. The biggest risk, and how to de-risk it

**The risk: nimbus's first contact with a real estate produces a false critical or a wrong fix, in front of the one engineer whose opinion decides adoption.** Everything in the repo has been proven against fakes. Real estates have policies with `NotAction`, conditions on `aws:PrincipalOrgID`, SCPs, VPC endpoints, NACLs, WAFs, Terraform modules three levels deep, and Kubernetes clusters with 400 RoleBindings. The second verifier found eight classes of false pass/positive without leaving the fakes. In my experience a tool that calls one private bucket "public" in week one is uninstalled in week two, and the engineer tells the next three companies. STRAT §4b says it plainly: "One false 'critical path' in a public demo kills credibility."

**De-risking, in order:**

1. **Run live now, on nimbus's own lab, nightly** (item 5). Then Azure and GCP in Q1. No README claim without a live run behind it.
2. **Shadow mode with three design partners.** Read-only role, `--no-network` except cloud APIs, run beside their Wiz/Prowler/Defender for 30 days under NDA. Publish agreement/disagreement counts per check class (not their data). Prowler got its breakthrough from AWS's blessing (`docs/research/strategy-how-to-win.md` §2.2); nimbus's equivalent is three named practitioners saying "it matched".
3. **A confidence label on every path and every "public"/"admin" claim**: `verified` (probe or simulator evidence), `evaluated` (policy evaluator with full inputs), `heuristic` (name/tag inference). Heuristic claims never produce a Critical. This is cheap (an attribute on the edge and Issue) and it is how SentinelOne's "Exploit Evidence" tab and FortiCNAPP's "no data ≠ 0" work (`docs/research/competitors/cnapp-leaders.md` best-in-class table).
4. **Cross-check IAM against the cloud's own oracle.** Every e2e run samples ≥50 (principal, action, resource) triples and compares the evaluator with `iam:SimulatePrincipalPolicy`; disagreement fails the build (gap analysis O16 acceptance).
5. **No PR without `terraform validate` and a plan that shows only the intended attribute changes** (RM2 acceptance below). Never auto-merge. Every PR body carries rollback.
6. **Coverage honesty in every output**: what was denied, skipped or timed out (Track G `coverage` table) so a missed finding is "not seen" rather than "secure".

The second-biggest risk is the single-maintainer bus factor (the number-one stall pattern in `docs/research/strategy-how-to-win.md` §2.3). Vendor-health rows on an RFP sheet are worth 5–14% and a zero there is survivable; a false critical is not. Mitigation sits in Phase 4 (two maintainers from two organisations, CNCF sandbox, support contracts).

## 6. The implementation plan

### 6.0 Ground rules for "best features, not just many"

The owner's clarification is the right one. A checkbox count is how vendors win RFPs and lose renewals. The rules this plan uses:

- **A capability is "shipped" only when it meets the best-in-class bar in its row below and passes its acceptance test on the lab (local and, where applicable, live).** Below that bar it is labelled `experimental` in `docs/checks.md`/README and does not appear in the comparison matrix.
- **Best-in-class has four parts, judged per row:** *precision* (no claim without an evidence tuple: source API call, statement/rule, timestamp), *depth* (matches the named leader's documented behaviour on the lab), *UX* (one command or one click; the output explains itself without a docs lookup), *evidence* (every number is reproducible from stored data; every path has per-hop `because`).
- **Differentiation rank (Diff)** is my answer to "how much would being best-in-class here make me pick nimbus?": **5** = nobody has it or only closed vendors do and nimbus can publish it; **4** = only paid tiers have it; **3** = shortlist criterion where parity is needed and an open implementation is credible; **2** = table stakes, parity is enough; **1** = low buyer pull or out of scope; **0** = do not build (ingest or defer).
- **Effort** uses the gap-analysis scale (S ≤ 2 agent-days, M ≤ 1 week, L ≤ 3 weeks, XL > 3 weeks). **Phase** points to section 6.2.

### 6.3 Verification discipline (non-negotiable, from the rulebook)

- Failing test first for every item; the test name appears in the session log with its red output.
- Independent Opus verifier per track re-runs the track's tests *and* the original probes, then tries to break it; findings return to the track before acceptance (this is what found D1–D8).
- `make verify` (vet, tests, pytest, ui-smoke, govulncheck, gosec high, groundtruth local; groundtruth live nightly) must be green for any "done".
- Every public claim (README, docs, benchmark page) is traceable to a test or a live-run artefact. A claim without one is removed, as Track E did with the README overclaims.
- Implemented ≠ deployed ≠ verified: the status table in `.planning/STATE.md` carries all three columns per capability row above.

### Closing opinion

If I were running the RFP today, nimbus would not be on the sheet; the engineer who already runs Prowler would bring it in through the side door, and that is how every tool in this category that mattered got in. Plan v2 has the right spine for that side door. What it lacks is the floor an RFP demands (frameworks, SIEM formats, governance, exec report, SSO-lite), honesty about Phase 0 not being done, and the one thing that converts a clever tool into a trusted one: running it, nightly, against a real cloud, and publishing what it got wrong as well as what it got right. Do items 1–10 in the next two weeks, and the Q4 claim is defensible. Skip item 5 and nothing else matters.
